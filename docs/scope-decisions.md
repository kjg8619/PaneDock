## D1. 2026-09-16 — Herdr 내부 pane 자동 추적을 지원 범위에서 제외

### 배경

Herdr를 첫 지원 조합의 포커스·경로 소스로 쓰는 계획을 세우고 진단 프로토타입까지 만들었다.
그러나 실제 사용 환경에서 치명적인 문제가 확인됐다(`docs/verification.md` V3).

- 로컬 Ghostty 화면은 그대로인데, **원격 SSH Herdr 클라이언트가 workspace를 바꾸면
  서버 전역 `focused_pane_id`가 원격 쪽을 따라갔다.**
- 원인: `session.snapshot.focused_*`는 서버 전역 `state.active` 기반이고, 전역은
  마지막으로 탐색한 클라이언트를 따른다(`src/app/api/session.rs:19-30`).
- 클라이언트별 위치는 서버가 **내부적으로** 갖고 있지만(`ClientShellLocation`),
  그것을 읽는 공식 API가 없다(`Method` enum에 클라이언트 읽기 메서드 없음).
- 확정된 세대 원인 중 하나는 **원격 클라이언트였다**: TTY 기준으로 로컬은 `ttys000`,
  원격은 `sshd-session` 하위의 `ttys021`(회사 PC, Tailscale)이었다.

해결하려면 Herdr 쪽에 읽기 경로를 추가해야 했다(스파이크의 C1 안: 클라이언트가 자기 위치를
상태 파일로 발행). `docs/local-client-focus-spike.md`가 그 계획이다.

### 결정

> **Herdr 자체 수정이 필요하다면 PaneDock에서 Herdr 연동을 지원하지 않는다.**

지원 원칙:

1. 대상 앱의 **소스 수정, 패치 바이너리, 별도 포크를 요구하지 않는다.**
2. **공식 API·CLI·문서화된 연동**으로 확인할 수 있는 범위만 지원한다.
3. 셸 설정 변경이나 별도 연동 설치가 필요하면 **먼저 설명하고 승인받는다.**

따라서 **Herdr 내부 pane 자동 추적은 이번 지원 범위에서 제외한다.**
Herdr 없이 그 목적을 달성할 다른 우회 방법을 추가로 조사하는 것도 이번에는 하지 않는다.

### 결과

| 항목 | 상태 |
| --- | --- |
| C1(클라이언트 측 상태 발행) | **미구현 · 진행 취소.** 계획 문서만 보존한다 |
| 패치·포크·별도 빌드 | **취소.** herdr 소스는 조사 목적으로만 `/tmp`에 받았고, 빌드·적용하지 않았다 |
| 운영 Herdr 바이너리·서버·세션·원격 연결 | **건드리지 않았다** |
| 기존 Herdr Adapter 코드 | **실험 코드로 보존.** `--adapter herdr`로만 도달하며 정상 실행 경로가 아니다 |
| 첫 검증 후보 | **Ghostty + 로컬 셸 + Ghostty 자체 분할 pane**으로 전환 |
| 기획서 원본 | 수정하지 않음(이 문서로 대체 기록) |

### 대체 후보와 근거

`Ghostty + 로컬 셸 + Ghostty 자체 분할 pane`을 첫 검증 후보로 삼는다.

- Ghostty는 **공식 AppleScript API**로 `focused terminal`과 `working directory`를 제공한다
  (1.3.0+, 설치본 1.3.1).
- 경로는 surface의 **live pwd**이며 셸 연동(`shell-integration = detect`, features에 `path`)이
  갱신한다.
- **셸 설정 변경도 별도 설치도 필요 없다** (Ghostty의 셸 연동은 앱 내장).
- herdr·tmux 같은 중첩 멀티플렉서는 이 검증에서 제외한다.

### 남는 한계 (지원 주장에 반영할 것)

- 중첩 TUI가 대상 terminal을 점유하면 보고되는 경로는 **바깥 프로세스의 cwd**이지
  그 TUI의 내부 프로젝트 경로가 아니다. 공식 조회로 중첩 여부를 확실히 판별할 수 없다.
  → **"자동 감지 완료"라고 표기하지 않는다.** 직접 셸 환경 전용임을 명시한다.
- Herdr 환경에서의 자동 추적은 **지원하지 않는다.** Herdr 안에서 작업하는 사용자에게는
  이 연동이 바깥 터미널 정보만 준다.

### 재검토 조건

- Herdr가 **클라이언트별 포커스를 읽는 공식 API**를 제공하면 재검토한다.
- 또는 로컬 클라이언트를 공식 수단만으로 확정할 방법이 문서화되면 재검토한다.

## V18 방향 확정 (2026-09-18) — 구성형 Dock: 공통 구성 + 자동 프로젝트 영역

**이 절은 제품 방향(무엇을 만들기로 했는가)만 기록한다. 구현·검증 결과는 `verification.md`에 쓴다. 두 문서를 섞지 않는다.**

### 1차 목표 (이번 개발 대상)

공통 앱·카드는 그대로 유지하고, **사용자가 배치한 프로젝트 영역 하나만** 포커스된 pane의 경로에 따라 자동으로 바뀌는 Dock.

### 로드맵 (이번에는 구현하지 않음)

프로젝트마다 **Dock 전체 구성**이 바뀌는 방식. 현재의 부분 전환을 **대체하는 것이 아니라**
향후 **선택 가능한 확장 방향**으로 둔다. 이번 구현에서 프로필 개념을 만들지 않는다.

### 사용자 경험 원칙

| 원칙 | 내용 |
| --- | --- |
| 표현 | **앱은 아이콘 중심, 카드는 내용 중심.** 둘을 한 줄에 섞되 아이콘과 폭이 다르다 |
| 공통 항목 | 프로젝트와 무관하게 유지. **"공통은 왼쪽" 같은 고정 배치를 강제하지 않는다** |
| 프로젝트 영역 | 첫 구현은 **사용자가 옮길 수 있는 영역 1개**. 전환 시 **그 영역의 내용만** 바뀐다 |
| 너비 | 프로젝트 항목 수가 달라도 **공통 항목 위치가 밀리지 않도록** 영역에 할당된 너비 안에서 `더보기`로 처리 |
| 상태 | **공통 카드의 실행 상태(예: 타이머)는 프로젝트 전환으로 초기화하지 않는다** |
| 실패 표시 | 미등록 경로·확인 불가·유지 상태는 **프로젝트 영역 안에서** 구분. 공통 앱·카드는 계속 쓸 수 있어야 한다 |
| 진단·보조 | 큰 진단 배지와 고정 조작 버튼의 비중을 줄이고, 기존 **상세 보기·작은 메뉴**로 접근을 유지 |

### 이번 구성요소

기존 앱·폴더·링크 + **프로젝트 영역** + (추가·제거 가능한) **시계/날짜 카드**, **집중 타이머 카드**.
카드는 **실제 정보를 표시하고 Dock 안에서 동작**해야 한다 — 시계 앱·타이머 앱을 여는 바로가기로 대신하지 않는다.
타이머는 **시작·일시정지·재설정**까지만. 통계·계정·프로젝트별 시간 기록은 넣지 않는다.

### 최소 구조 (구분만 둔다)

**배치(batch)** · **프로젝트 내용** · **카드 실행 상태**를 서로 다른 것으로 다룬다.
전체 Dock 프로필 전환은 만들지 않는다.

### 이번 범위 밖

Herdr · 새 Adapter · 외부 서비스 위젯 · 대규모 플러그인 시스템 · **Dock 전체 프로필 전환** · 접기 기능 확장.

### 진행 순서

1. **기준 화면 제안**(레퍼런스 대비) → **사용자 확인** — 프로젝트 A / B / 미등록 경로를 같은 배치로 제시
2. 승인 후 구현: 실행·프로젝트 전환 연결 → 시계·타이머 실제 동작 → 편집기에 **배치 미리보기**(공통·카드·프로젝트 영역 순서 변경) → 저장·취소·재실행 복원 → 기존 설정 호환


### 승인된 배치 (사용자 확인 2026-09-18, 위젯형)

시안 `/tmp/v18/pane-dock-v18-proposal.html` — **위젯형**으로 승인됨("저런 방향으로 진행").

| 요소 | 규격 |
| --- | --- |
| 바 | 높이 **104pt**(기존 76 → 확대), 둥근 모서리 26, 유리 패널 |
| 공통 앱 | **68pt 타일**(radius 17, 그라데이션 + 하이라이트 + 그림자), 실행 중이면 하단 점 |
| 시계 카드 | **아날로그 미니 시계**(초 진행 링 + 시·분침) + 큰 시간 + 날짜 |
| 타이머 카드 | **진행 링**(남은 비율) + 가운데 `mm:ss` + 원형 `▶ ❚❚ ↺` |
| 프로젝트 항목 | **48pt 타일**(폴더 = 색 + 이니셜, 링크 = 아이콘), 넘치면 `⋯` 타일 |
| 프로젝트 영역 | 폭 고정(기본 **360pt**), 점선 = 사용자가 옮길 수 있는 영역, 라벨 칩 |
| 상태·조작 | 큰 진단 배지 → **점 하나**, 고정 버튼 6개 → 오른쪽 **`⋯` 메뉴**(상세 보기 유지) |

### 자료 구조 (최소 구조 — 세 가지를 구분만 한다)

| 구분 | 어디에 | 저장 |
| --- | --- | --- |
| **배치** | `settings.json`에 `layout` 신설 — `order`(공통/카드/프로젝트 영역 순서), `projectAreaWidth`, `cards[]`(id·종류·추가·제거) | **저장**(바뀐 것만) |
| **프로젝트 내용** | 기존 `projects.json`(항목·ID·순서 그대로) | **저장**(기존 규칙) |
| **카드 실행 상태** | 메모리(타이머 진행·일시정지) | **저장하지 않음** — 프로젝트 전환·재실행으로 초기화되지 않게 메모리에 유지 |

**호환:** `layout`이 없는 기존 설정은 승인된 기본 배치로 읽는다. 항목·ID·순서는 **기존 파일을 그대로** 쓰고,
공통 항목은 공통 영역으로, 프로젝트 항목은 프로젝트 영역으로 **표시만** 나눈다(데이터 이전 없음 → 되돌릴 수 있다).

### 구현 순서 (승인 후)

1. `DockBarLayout`에 새 규격 상수 + `DockView`를 타일/위젯 구조로 교체(실행·전환 연결 유지)
2. 시계 카드(초 단위 갱신) · 집중 타이머 카드(시작·일시정지·재설정, 메모리 상태)
3. 편집기에 **배치 미리보기** + 순서 변경(공통/카드/프로젝트 영역) + 영역 폭
4. 저장·취소·재실행 복원, 부분 실패 안내 유지
5. 자체 검사 추가(순서 저장·복원 / 미등록·확인 불가 / 카드 상태가 전환으로 초기화되지 않음) + 회귀


### 결정 보정: 카드 실행 상태의 "메모리" 의미 (2026-09-18)

앞 절의 "메모리만 저장하면서 재실행에도 유지"는 **앱 실행 중**을 뜻한다.

- 카드 실행 상태(타이머 진행·일시정지)는 **파일에 저장하지 않는다.**
- 유지되는 범위: **앱이 실행 중인 동안** — 프로젝트 전환, 접기/펼치기, 배치 변경, 뷰 재생성으로 **초기화되지 않는다.**
- **앱 완전 종료 후 복원은 이번 범위가 아니다**(다음 단계 후보).
- 남은 시간은 표시 갱신 횟수가 아니라 **시각 기준**으로 계산한다(갱신이 밀려도 값이 맞는다).

## D2. 2026-09-18 — 사용 모드 확정: Mac Dock / Custom Dock (Both는 V20.2)

### 배경

지금까지 PaneDock은 **기본 macOS Dock을 건드리지 않는다**는 원칙(V18 이전)으로 커스텀 바를 화면 하단에 띄웠다.
사용자가 “화면 하단을 실제로 쓰는” 사용 모드를 확정하면서, 이 원칙을 **동의 기반 대체 모드**로 정정한다.

### 결정

| 모드 | 내용 | 이번 범위 |
| --- | --- | --- |
| **Mac Dock** | 기본 macOS Dock을 **원래 설정 그대로** 둔다. PaneDock 커스텀 화면은 표시하지 않는다. 메뉴바에서 설정·모드 전환·종료 | 구현 |
| **Custom Dock** | **사용자 동의 후** 기본 Dock을 숨기고 PaneDock을 화면 하단 주 Dock으로 배치. 모드 해제·정상 종료 시 PaneDock이 바꾼 설정을 복원 | 구현 |
| **Both** | 기본 Dock 유지 + PaneDock을 왼쪽/오른쪽 **호출형 패널**로 사용 | **V20.2(미구현)** — 정책·확장 지점만 정의하고, 작동하는 선택지로 제공하지 않는다 |

> **정책 정정:** “기본 Dock 설정 변경 금지” → **“사용자가 동의한 대체 모드에서 필요한 설정만 변경하고 복원한다.”**

### 원칙

1. **동의 없이는 시스템 설정을 바꾸지 않는다.** 첫 Custom 적용에서 변경 항목·복원 방법을 설명하고 동의를 받는다.
   기존 설정에 `mode`가 없으면 **동의한 것으로 간주하지 않는다.**
2. **선택과 적용을 구분한다**(선택만으로는 시스템이 바뀌지 않는다). 화면에는 선택한 모드와 **실제 적용 상태**를 따로 표시한다.
3. **되돌릴 수 있게 바꾼다.** 변경할 키의 원래 값·자료형·존재 여부를 기록하고, **실제로 바꾼 키만** 원래대로 되돌린다
   (없던 키는 삭제). 전체 Dock 설정을 덮어쓰거나 초기화하지 않는다.
4. **재등장 억제에 추가(문서화되지 않은) 설정이 필요하면 먼저 제시하고 승인받는다.** 승인 없이는 공식 자동 숨김까지만 쓴다.
5. **Dock 삭제·보안 기능 해제·반복 강제 종료는 쓰지 않는다.** Dock 재시작은 설정 반영을 위한 **1회**만 한다.
6. **Mac Dock 모드에서는** 기본 Dock의 앱 목록·순서·크기를 관리하지 않고, PaneDock 단축키로 커스텀 화면이 **몰래 뜨지 않는다.**
7. 접기·펼치기·일시 숨김은 **모드 변경이 아니다** — 이때마다 기본 Dock 설정을 다시 쓰지 않는다.
8. 프로젝트별 전체 Dock 구성 전환은 **이후 로드맵**이다(1차 원칙: 공통 앱·카드 유지, 프로젝트 영역만 경로에 따라 바뀜).

### 검증 원칙

- 자동 검사는 **시스템 Dock 제어를 대체한 테스트 구현**으로 적용·실패·복원·중복 요청을 확인한다.
  **자동 검사에서 실제 시스템 Dock 설정을 건드리지 않는다.**
- 실제 설정 변경·Dock 재시작이 필요한 GUI 검증은 **변경 항목·영향·복구 방법을 제시하고 별도 승인**을 받는다.
